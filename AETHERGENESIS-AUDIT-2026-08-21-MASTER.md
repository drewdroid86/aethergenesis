## FINDING #1 (root architecture issue) — per-star-orbits, now fully traced end to end

This is the single highest-value fix in the codebase — it's not just a rendering quirk, it corrupts the actual habitability/civilization scoring too. Full chain, three files:

**`nbodyWorker.ts`** — module-level state (`bodies`, `centralMass_solar`) is set exactly once via `INIT` and never updated. `useSimulation.ts:332` creates the one and only `Worker` at mount and seeds it with hardcoded Earth/Jupiter/Halley at `centralMass_solar = 1.0` (line 345) — real orbital elements, real masses, but always this one specific system.

**`engine.ts`** — reads `this.nbodyBuffer` once per frame (line 307) and passes the *identical* buffer into every hero star's `.update()` in the render loop (389→421→487). Every star in the field — could be dozens depending on tier — renders its planets from the same three-body dance. Zoom out and every star's planets move in perfect lockstep: same phase, same angle, same speed, whether the star is a 0.09-solar-mass red dwarf or a 100-solar-mass hypergiant.

**`SimulationCoordinator.ts:141`** — and this is the part that isn't just visual: `processSimulationState()` back-computes each body's semi-major axis via the vis-viva equation (`invA = 2/r - v²/GM`, correct formula) — but uses `G_M = 4π² × perStarState.mass_solar`, i.e. **the selected star's real mass**, to reinterpret position/velocity data that was generated by the worker under a permanently-fixed `GM = 4π² × 1.0`. That computed semi-major axis then feeds directly into `AstrobiologyEngine.evaluatePlanet()` (line 182), which uses it to compute effective stellar flux, habitable-zone membership, biomass, and civilization tier. A heavier star doesn't just show the wrong-looking orbit — it makes the *same* fixed trajectory compute as artificially closer-in (hotter, less habitable) than a lighter star would for the identical trajectory, purely as a side effect of which star happens to be selected. None of it reflects real orbital mechanics for that star, because the trajectory itself was never generated under that star's gravity.

**Two known symptoms, now explained as the same root cause:**
- `loadStarPreset()` (`useSimulation.ts:140`) calls `star.applyPreset()`, which correctly updates the star's own temperature/size/phase rendering — but never touches the worker, so a preset's mass never reaches the orbits.
- `addBodyToSimulation()` (`useSimulation.ts:152`) computes a new body's *initial* velocity correctly using the selected star's real mass, then hands it to a worker whose ongoing integration is permanently locked to `G × 1.0` — a body added to any star heavier than 1 solar mass launches with velocity tuned for stronger gravity than it'll actually experience, and will drift onto an increasingly wrong (likely unbound) trajectory.

**Fair to the code:** the integrator itself (`nbodyWorker.ts`) is genuinely solid — Velocity-Verlet, softened gravity, NaN guards, a 200 AU distance clamp, double-buffered zero-allocation transfers. `OrbitalMechanics.ts`'s Kepler solver and Keplerian→Cartesian conversion are correct, standard astrodynamics, verified by hand. `SimulationCoordinator`'s vis-viva back-calculation is the right formula, just fed the wrong mass for the data it's interpreting. This is an architecture problem (one shared worker instance), not a math problem.

**Not yet checked:** whether `CometSystem.ts` and `AsteroidBeltSystem.ts` make the same shared-buffer assumption, and whether `StellarPhysics.ts` (502 lines, completely unread so far) or `engine.ts` (547 lines, only grepped) have anything else relevant to a fix here.

## FINDING #2 — `AstrobiologyEngine.ts` harsh reset-on-dip

`timeInHz_yr` (line 118-123) resets fully to zero the instant `compositeScore` dips to 0.65 or below for even one tick — no grace period, no decay curve. Since `compositeScore` is a product of five independent 0-1 sub-scores (orbital, thermal, atmosphere, stellar-activity, age), any one of them dipping is enough to wipe out however much accumulated time-toward-biogenesis a planet had, even after billions of years. Combined with a genuinely eccentric orbit (once per-star-orbits is fixed and real per-star orbits exist), this could make civilizations very hard to ever reach for planets that are habitable on average but swing outside the threshold briefly each orbit. Worth a design decision — may be intentional ("habitability should feel precarious"), but worth confirming rather than assuming.

Also worth noting: `isInHabitableZone` (returned to the UI) and the `timeInHz_yr` accumulation gate (`compositeScore > 0.65`) are different conditions — a planet can show `isInHabitableZone: true` while its biomass timer isn't running, because the composite score also factors in thermal/atmosphere/age/stellar-activity. Not a bug, but a naming trap if the UI ever surfaces `isInHabitableZone` as a promise that biomass is accumulating.

**Verified correct, not a bug (I checked this specifically since it's an easy swap to get backwards):** the habitable-zone flux boundary logic (`S_eff < 1.1 && S_eff > 0.53`) is oriented correctly — inner/hot edge at the higher flux threshold, outer/cold edge at the lower one, matching the simplified Kopparapu et al. parameterization.

## FINDING #4 — MCP dev-tooling (`server/mcp/*.mjs`), all three fully read
These are real, correctly-wired stdio MCP servers (Google's `@modelcontextprotocol/sdk` is a genuine dependency) — not dead code, despite not being imported anywhere in `server.ts`. That's expected: MCP servers connect via an external client config, not an import.

- **`sim-state.mjs`** (live WebSocket bridge to the running sim): `trigger_simulation_event`'s tool description says *"disabled by default for safety"* but nothing in the code gates it — `force_supernova`, `reset`, `impact_event` all fire unconditionally whenever the socket's open. Either the doc is stale or a planned safety gate never got built. Verified clean: `WS_TOKEN` auth is correctly guarded — `SimStateSocket.ts` refuses to start in production if the token is still the default — and reconnect backoff is properly capped.
- **`nasa-horizons.mjs`**: `search_small_bodies`'s JPL-failure fallback silently substitutes a hardcoded 5-comet/5-asteroid list with no field marking it as fallback data — indistinguishable from live JPL data to a calling agent. Verified clean: AU/day→km/s and light-minutes/AU constants are both correct to the physical constant by hand-check; timeout/abort handling is correct.
- **`stellar-catalog.mjs`** (biggest finding of the three): `get_star_by_name` has no "not found" path at all — an unmatched name (typo, nonexistent star, *or* a legitimate zero-row SIMBAD response) returns the Sun's entire physical profile with the label swapped to whatever name was searched, distinguished only by a `source: 'cached_preset'` field. Also: `estimateParams()`'s luminosity-class detection does a naive `.includes('I')` check — correctly catches supergiants (`I`) and giants (`III`, checked first), but subgiants (`IV`) and bright giants (`II`) both contain the letter `I` too, so they wrongly get the full supergiant ×100 radius / ×10 mass multiplier. Minor: `sanitizeAdql()` gets called twice on the same value (line 580, then again 593 in `search_stars`), doubling any escaped quotes — would mangle a spectral-class search containing an apostrophe, low real-world impact. Verified clean: the ADQL escaping itself is correctly implemented, no injection path found.
